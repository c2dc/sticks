## Problemas encontrados e resolvidos (em ordem)

Subir o laboratório expôs uma cadeia de defeitos reais, todos corrigidos:

1. **Imagem Kali com 403 (herdado).** Já resolvido na sessão anterior (imagem
   enxuta). O build do laboratório partiu daí.

2. **Caldera só subia o FTP (2222), nunca a API web (8888).** Causa raiz: o
   bind-mount `./.docker/caldera:/usr/src/app` sobrepunha a imagem com o diretório
   do host, que não tinha a UI compilada (`magma/dist`). Sem a UI, o servidor web
   não subia. Além disso, o mount forçava `os.walk` sobre o `atomic-red-team`
   gigante pelo filesystem lento do Docker Desktop (Windows→Linux), travando a
   verificação de abilities no boot (confirmado via faulthandler: preso em
   `data_svc._verify_abilities` → `file_svc.walk_file_path`). **Correção:**
   removido o bind-mount (a imagem já contém código + UI + dados) e instalado o
   módulo python `docker` (plugin `builder`). Caldera passou a subir healthy.

3. **Alvos nginx/db não subiam (apt em runtime sem internet).** Os scripts
   `*_sut{a,b}.sh` faziam `apt-get install`/`pip install` em runtime, mas as
   redes dos alvos são `internal: true` (sem egress), então travavam. **Correção:**
   instalação movida para o BUILD-TIME dos Dockerfiles (onde há internet); em
   runtime os scripts só configuram e sobem serviços; apt/pip viram no-op
   tolerante. Removido `rar` (inexistente no Debian trixie) → `p7zip-full`.
   Healthcheck do db ganhou start_period adequado.

4. **Conflito de subnet com outro projeto local (volaura).** A rede
   `volaura_default` ocupa 192.168.10.0/16, colidindo com a 172.20/172.23 do lab.
   **Correção não-destrutiva:** criado `docker/docker-compose.override.yml`
   (ignorado no git) que remapeia APENAS nesta máquina caldera-kali→172.30 e
   mgmt→172.33. O código versionado permanece em 172.20/21/22/23 (agnóstico à
   máquina). As redes de ataque 172.21/172.22 (que os comandos miram) ficam
   intactas.

5. **Operação real rodava com chain vazia (0 links).** O `OperationRunner`
   carregava as abilities mas **nunca carregava o adversary** na Caldera, usava
   planner `atomic` (o lab usa `batch`) e fazia um **poll único imediato**.
   **Correção (backend):** `CalderaClient.load_adversary` (POST
   /api/v2/adversaries, idempotente) + `poll_until_complete` (aguarda estado
   terminal); runner carrega o adversary, usa planner `batch`/group `red` e
   aguarda a conclusão; endpoint passa o payload do adversary. `load_ability`/
   `load_adversary` idempotentes (tratam "already exists" via PUT) para o teste
   ser repetível.

## Observações para o usuário

- O remapeamento de subnet está só no override local; se rodar em outra máquina
  sem o conflito do volaura, o compose base (172.20) funciona direto. Se o
  conflito existir, recrie o `docker-compose.override.yml` (ou pare o volaura).
- Para subir o lab: `cd docker && docker compose up -d caldera kali nginx db`
  (o override é aplicado automaticamente). Caldera leva ~2-3 min para ficar
  healthy; o kali reinicia até a Caldera responder, então estabiliza.
- Para rodar o E2E real: `cd pipeline_ui/backend; $env:PIPELINE_UI_LAB="1";
  .\.venv\Scripts\python.exe -m pytest -m lab`. Leva ~5 min (execução real).
- A UI pode ser aberta para acompanhar o pipeline (frontend 15173 / backend
  8010) — o passo a passo visual do CostaRicto que você pediu pode ser feito
  por cima deste ambiente já funcional quando quiser.
