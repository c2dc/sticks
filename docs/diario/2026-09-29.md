# Diário — 29 de setembro de 2026

## Objetivo

Auditar no navegador o fluxo completo da campanha ShadowRay, confrontar a
interface com a especificação do Kiro, localizar bloqueios do laboratório real
e deixar o projeto em um ponto seguro para continuidade.

## Avanços comprovados

- A interface foi executada sem ocupar a porta 8000: frontend em `15173` e
  backend de validação em `18080` durante a auditoria.
- O Estágio 1 exibiu 10 técnicas ATT&CK, 9 relacionamentos, 14 indicadores,
  2 itens de infraestrutura, 2 malwares e metadados.
- O Estágio 2 exibiu 11 Abilities curadas, seus comandos, ordenação,
  dependências e o Adversary ShadowRay.
- O Estágio 3 exibiu as 11 Abilities, abriu a confirmação explícita e mostrou
  os comandos concretos e destinos antes da execução.
- Os destinos observados ficaram restritos ao laboratório: nginx
  `172.21.0.20`, db `172.22.0.20` e executor local para comandos `echo`.
- O Adversary ShadowRay foi carregado na Caldera durante o ensaio.
- Foi corrigido o payload de Ability enviado à Caldera para preservar
  `technique_name`, campo exigido pela API real.
- Respostas 4xx/5xx da Caldera agora são traduzidas pelo backend para HTTP 502
  com diagnóstico estruturado, em vez de gerar erro interno genérico.
- A visão do pipeline agora assina os três canais de estágio e recalcula o
  bloqueio sequencial após cada transição.
- O cliente WebSocket não reconecta indefinidamente quando o backend encerra
  normalmente um fluxo terminal.
- O Docker Compose ganhou uma subnet de gerenciamento explícita
  (`172.23.0.0/24`) e healthchecks reais para o alvo web e a Caldera.
- O utilitário `load_adversary.py` passou a usar saída UTF-8 no Windows.
- As portas padrão da aplicação foram alinhadas para `15173` (frontend) e
  `8010` (backend publicado), preservando a porta 8000 para outro projeto.

## Problemas encontrados durante o laboratório real

1. A imagem Kali baixou cerca de 2,4 GB e a instalação falhou porque o espelho
   rolling retornou HTTP 403 para sete pacotes. Essa etapa não foi repetida.
2. A rede de gerenciamento dinâmica escolheu inicialmente uma faixa que se
   sobrepunha a `172.20.0.0/24`; a faixa agora é fixa em `172.23.0.0/24`.
3. Os healthchecks anteriores executavam apenas `true`, declarando serviços
   saudáveis antes de estarem prontos. Eles foram substituídos.
4. A inicialização completa da Caldera é lenta ao indexar o catálogo Atomic.
5. A primeira execução real parou porque `technique_name` não era enviado. O
   defeito foi corrigido, mas o laboratório completo ainda precisa ser repetido
   para comprovar execução, resultados e auditoria reais de ponta a ponta.

## Evidências automatizadas

- Backend: suíte sem laboratório real executada após as correções.
- Frontend: 18 testes Vitest aprovados em 6 arquivos.
- Frontend: build de produção Vite aprovado.
- O teste de laboratório real permanece opt-in por segurança
  (`PIPELINE_UI_LAB=1`) e não é executado na suíte comum.

## Ponto exato de continuidade

1. Resolver a construção da imagem Kali contra o espelho rolling (retry,
   espelho alternativo confiável ou redução dos metapacotes).
2. Subir o Compose e aguardar os healthchecks reais.
3. Carregar o ShadowRay e repetir a confirmação no Estágio 3.
4. Verificar na interface os 11 resultados, os totais agregados e a trilha de
   auditoria persistida.
5. Somente depois marcar as tarefas 6.4, 15.3 e o checkpoint final 16 no Kiro.

## Comandos de retomada

```powershell

# backend publicado/local na porta 8010
```

# Diário — 29 de setembro de 2026 (segunda parte: DX e ajustes de interface)

Bloco de trabalho posterior à auditoria do ShadowRay, focado em experiência de
desenvolvimento (um único comando para subir tudo) e em ajustes de interface
pedidos durante o uso: tamanho da tipografia, logo, tema e o seletor de idioma.

## Objetivo

Tornar o dia a dia de desenvolvimento mais simples (um comando na raiz sobe todo
o sistema) e corrigir pontos de usabilidade percebidos ao abrir o site: letras
pequenas, logo pequena, tema que não respeitava o sistema operacional e voltava
ao claro ao recarregar, e o seletor de idioma que mostrava "BR"/"US" em vez das
bandeiras.

## Avanços comprovados

### Comando único de desenvolvimento (raiz)

- Foi criado um `package.json` na raiz do repositório com um script `dev` que
  sobe **backend + frontend + migração do banco** de uma só vez, usando
  `concurrently`. Antes era necessário abrir dois terminais e rodar cada parte
  separadamente.
- O comando aplica as migrações Alembic antes de iniciar o backend, então o
  banco SQLite fica pronto automaticamente. Não há serviço de banco separado
  para subir em desenvolvimento.
- Portas mantidas: frontend em `15173` e backend em `8010`.

### Um único `node_modules` (npm workspaces)

- O projeto passou a usar **npm workspaces**: agora existe um único
  `node_modules` na raiz, compartilhado pelo `concurrently` e pelas dependências
  do frontend (React, Vite, etc.). O antigo `node_modules` dentro de
  `pipeline_ui/frontend` deixou de existir, assim como o `package-lock.json` do
  frontend (consolidado no lockfile da raiz).
- Observação de contexto: backend e banco não usam `node_modules` — o backend é
  Python (dependências no `.venv`) e o banco é um arquivo SQLite. A unificação
  diz respeito apenas à parte Node (frontend + ferramenta de orquestração).
- `npm run setup` agora instala tudo com um único `npm install` na raiz.

### Redução do ruído de logs

- `uvicorn` roda com `--log-level warning` e `--no-access-log` (sem uma linha de
  log por requisição).
- O logger do Alembic foi rebaixado para `WARNING` no `alembic.ini`, removendo
  as mensagens `INFO` da migração.
- Os scripts internos rodam em modo silencioso, eliminando o eco do npm. O
  resultado é uma saída enxuta, essencialmente a URL do Vite e erros reais.

### Tipografia e logo

- A fonte base do site aumentou de 16px (padrão do navegador) para **18px** no
  `html`. Como o layout usa unidades `rem`, isso escala texto e espaçamentos de
  forma proporcional, sem quebrar o layout.
- A logo da barra de navegação aumentou: versão completa (desktop) de 36px para
  48px de altura; símbolo (mobile) de 36px para 44px; a barra passou de 56px
  para 64px de altura para acomodar a logo maior.

### Tema: respeitar o sistema e persistir corretamente

- O tema agora usa `localStorage` como fonte de verdade local, com
  `prefers-color-scheme` como padrão na primeira visita. Assim o site abre no
  modo escuro quando o sistema operacional está em modo escuro.
- Foi corrigido o bug em que o tema voltava ao modo claro a cada atualização de
  página. A causa raiz era dupla: o frontend dependia apenas de uma leitura de
  rede, e o backend nunca devolvia as preferências salvas. Agora a escolha
  sobrevive ao reload instantaneamente, sem depender da rede.
- Um pequeno script no `index.html` aplica o tema antes de o React montar,
  evitando o "flash" de tela clara ao recarregar.
- Correção de contrato no backend: `GET /api/estado-sessao` passou a devolver o
  bloco `preferencias` (tema + idioma). Antes o `PUT /api/preferencias` salvava,
  mas o `GET` nunca retornava o valor, então a preferência não era restaurada.
  Com isso a preferência também sincroniza entre máquinas.

### Seletor de idioma com bandeiras reais (SVG)

- O seletor de idioma mostrava "BR"/"US" em vez de bandeiras. A causa é uma
  limitação do Windows, que não inclui a fonte de emoji de bandeira, então os
  emojis `🇧🇷`/`🇺🇸` caem para as letras.
- A solução foi substituir os emojis por bandeiras em **SVG vetorial**
  (componentes `FlagBR`/`FlagUS`), que renderizam de forma consistente em
  qualquer sistema operacional, sem adicionar dependências e sem usar imagens
  de bandeira "falsas".

### Remoção do seletor de "paleta de times"

- O antigo painel de preferências tinha um seletor de paleta blue/red/purple
  team. Ele já não fazia parte da navbar; as chaves de tradução órfãs
  (`palette.*`) foram removidas dos arquivos `preferences.json` (pt-BR e en). O
  site mantém sua própria paleta de cores, funcionando em modo claro e escuro.

## Evidências automatizadas

- Frontend: `tsc --noEmit` (type-check) sem erros após as mudanças.
- Backend: suíte completa executada com **177 testes aprovados** (1 teste de
  laboratório real desmarcado por padrão).
- Verificação manual ao vivo: `GET /api/estado-sessao` passou a retornar
  `"preferencias": { "tema": ..., "idioma": ... }` após um `PUT`; backend
  respondeu `{"status":"ok"}` em `/health` e o frontend respondeu `200`.
- O banco de desenvolvimento foi reposto aos padrões (claro / pt-BR) após os
  testes manuais.

## Como rodar (novo fluxo)

```powershell
# a partir da raiz do repositório — sobe backend + frontend + migração
npm run dev

# em uma máquina nova, instalar tudo primeiro (um único node_modules na raiz)
npm run setup
```

Frontend em `http://localhost:15173`, backend em `http://localhost:8010`.
