## Problems encountered and resolved (in order)

Bringing up the lab exposed a chain of real defects, all fixed:

1. **Kali image with 403 (inherited).** Already resolved in the previous
   session (trimmed image). The lab build started from there.

2. **Caldera only brought up the FTP (2222), never the web API (8888).** Root
   cause: the bind-mount `./.docker/caldera:/usr/src/app` overlaid the image
   with the host directory, which did not have the compiled UI (`magma/dist`).
   Without the UI, the web server did not start. In addition, the mount forced
   `os.walk` over the giant `atomic-red-team` through Docker Desktop's slow
   filesystem (Windows→Linux), stalling the ability verification at boot
   (confirmed via faulthandler: stuck in
   `data_svc._verify_abilities` → `file_svc.walk_file_path`). **Fix:** removed
   the bind-mount (the image already contains code + UI + data) and installed
   the python `docker` module (plugin `builder`). Caldera then came up healthy.

3. **nginx/db targets did not start (apt at runtime without internet).** The
   `*_sut{a,b}.sh` scripts ran `apt-get install`/`pip install` at runtime, but
   the target networks are `internal: true` (no egress), so they stalled.
   **Fix:** installation moved to the Dockerfiles' BUILD-TIME (where there is
   internet); at runtime the scripts only configure and start services; apt/pip
   became tolerant no-ops. Removed `rar` (nonexistent on Debian trixie) →
   `p7zip-full`. The db healthcheck got an adequate start_period.

4. **Subnet conflict with another local project (volaura).** The
   `volaura_default` network occupies 192.168.10.0/16, colliding with the lab's
   172.20/172.23. **Non-destructive fix:** created
   `docker/docker-compose.override.yml` (git-ignored) that remaps ONLY on this
   machine caldera-kali→172.30 and mgmt→172.33. The versioned code stays at
   172.20/21/22/23 (machine-agnostic). The attack networks 172.21/172.22 (which
   the commands target) stay intact.

5. **Real operation ran with an empty chain (0 links).** The `OperationRunner`
   loaded the abilities but **never loaded the adversary** into Caldera, used
   the `atomic` planner (the lab uses `batch`), and did a **single immediate
   poll**. **Fix (backend):** `CalderaClient.load_adversary` (POST
   /api/v2/adversaries, idempotent) + `poll_until_complete` (waits for a
   terminal state); the runner loads the adversary, uses the `batch` planner /
   `red` group, and waits for completion; the endpoint passes the adversary
   payload. `load_ability`/`load_adversary` are idempotent (handle "already
   exists" via PUT) so the test is repeatable.

# Journal — October 1, 2026 (part 2: network migration to class C)

## Goal

At the user's request, replace the class B ranges (172.20/21/22/23.0.0/24) of
the SUT with class C ranges (192.168.x) to resolve the subnet conflict at the
root (making the local override obsolete) and adopt a more readable addressing
convention.

## Design decisions (confirmed with the user)

- **Class C /24** for the 4 networks (a few hosts per network is enough).
- **Last octet = machine identity** (not the position in the network): each
  host keeps the same final number on ALL its interfaces. Multiples of 10.
- Final scheme:
  - caldera-kali `192.168.10.0/24` — caldera `.10`, kali `.20`
  - kali-nginx   `192.168.20.0/24` — kali `.20`, nginx `.30`
  - nginx-db     `192.168.30.0/24` — nginx `.30`, db `.40`
  - mgmt         `192.168.40.0/24` — caldera
  - Reading: 3rd octet = network; 4th octet = machine. E.g., `192.168.20.30` =
    "kali-nginx network, nginx machine". kali is always `.20`, nginx always `.30`.

## Containment safeguard (user request)

Before choosing/bringing up, I checked what already exists on the machine
(Docker networks + host routes/interfaces). The ranges 192.168.56.0/24 (VMware)
and 192.168.72.0/24 (the "Internet" interface) are in use, but do NOT collide
with 10/20/30/40.

Created `docker/preflight-network-check.ps1`: before bringing up the lab, it
checks whether any of the 4 subnets is already in use (Docker network or host
route) and **aborts (exit 1)** on overlap — preventing attack packets from
being routed to destinations outside the lab. Run it before `docker compose up`.

## Scope and validation

- Consistent IP-to-IP translation across ~620 occurrences / 60 files: compose,
  16 setup scripts, the targets' web content, 8 ability JSONs, the validator +
  containment modules + runner, 14 tests, README/docs/specs.
- Local override and diagnostic files removed (obsolete).
- **Validation:** preflight OK (4 free subnets); lab up on the new IPs
  (caldera healthy, kali beacon ALIVE, nginx/db healthy, IPs match the scheme);
  mocked suite 188 passed; frontend type-check + 17 passed; **REAL ShadowRay
  E2E PASSED (~5min) on the new IPs**.
