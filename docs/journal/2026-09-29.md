# Journal — September 29, 2026

## Goal

Audit the full ShadowRay campaign flow in the browser, compare the interface
against the Kiro specification, locate real-lab blockers, and leave the project
at a safe point for continuation.

## Proven progress

- The interface ran without occupying port 8000: frontend on `15173` and the
  validation backend on `18080` during the audit.
- Stage 1 displayed 10 ATT&CK techniques, 9 relationships, 14 indicators,
  2 infrastructure items, 2 malware entries, and metadata.
- Stage 2 displayed 11 curated Abilities, their commands, ordering,
  dependencies, and the ShadowRay Adversary.
- Stage 3 displayed the 11 Abilities, opened the explicit confirmation, and
  showed the concrete commands and targets before execution.
- The observed targets stayed restricted to the lab: nginx
  `192.168.20.30`, db `192.168.30.40`, and a local executor for `echo` commands.
- The ShadowRay Adversary was loaded into Caldera during the rehearsal.
- The Ability payload sent to Caldera was fixed to preserve `technique_name`,
  a field required by the real API.
- Caldera 4xx/5xx responses are now translated by the backend into HTTP 502
  with structured diagnostics, instead of raising a generic internal error.
- The pipeline view now subscribes to the three stage channels and recomputes
  the sequential lock after each transition.
- The WebSocket client no longer reconnects indefinitely when the backend
  normally closes a terminal flow.
- Docker Compose gained an explicit management subnet
  (`192.168.40.0/24`) and real healthchecks for the web target and Caldera.
- The `load_adversary.py` utility now uses UTF-8 output on Windows.
- The application default ports were aligned to `15173` (frontend) and
  `8010` (published backend), preserving port 8000 for another project.

## Problems encountered during the real lab

1. The Kali image downloaded about 2.4 GB and the installation failed because
   the rolling mirror returned HTTP 403 for seven packages. This step was not
   retried.
2. The dynamic management network initially picked a range that overlapped
   `192.168.10.0/24`; the range is now fixed at `192.168.40.0/24`.
3. The previous healthchecks only ran `true`, declaring services healthy before
   they were ready. They were replaced.
4. Caldera's full startup is slow while indexing the Atomic catalog.
5. The first real execution stopped because `technique_name` was not sent. The
   defect was fixed, but the full lab still needs to be repeated to prove real
   end-to-end execution, results, and audit trail.

## Automated evidence

- Frontend: 18 Vitest tests passed across 6 files.
- Frontend: Vite production build passed.
- The real-lab test remains opt-in for safety (`PIPELINE_UI_LAB=1`) and does
  not run in the common suite.

# Journal — September 29, 2026 (part two: DX and UI adjustments)

A work block after the ShadowRay audit, focused on developer experience (a
single command to start everything) and on UI adjustments requested during use:
typography size, logo, theme, and the language selector.

## Goal

Make day-to-day development simpler (one command at the root starts the whole
system) and fix usability points noticed when opening the site: small text,
small logo, a theme that did not respect the operating system and reverted to
light on reload, and the language selector that showed "BR"/"US" instead of the
flags.

## Proven progress

### Single development command (root)

- A root `package.json` was created with a `dev` script that starts
  **backend + frontend + database migration** at once, using `concurrently`.
  Previously you had to open two terminals and run each part separately.
- The command applies the Alembic migrations before starting the backend, so
  the database schema is ready automatically. The database is the
  containerized PostgreSQL (`localhost:5432`), which must be up before
  `npm run dev`.
- Ports kept: frontend on `15173` and backend on `8010`.

### A single `node_modules` (npm workspaces)

- The project now uses **npm workspaces**: there is a single `node_modules` at
  the root, shared by `concurrently` and the frontend dependencies (React,
  Vite, etc.). The old `node_modules` inside `ui/frontend` no longer exists,
  nor does the frontend `package-lock.json` (consolidated into the root
  lockfile).
- Context note: the backend and database do not use `node_modules` — the
  backend is Python (dependencies in `.venv`) and the database is the
  containerized PostgreSQL. The unification concerns only the Node part
  (frontend + orchestration tool).
- `npm run setup` now installs everything with a single `npm install` at the
  root.

### Reduced log noise

- `uvicorn` runs with `--log-level warning` and `--no-access-log` (no log line
  per request).
- The Alembic logger was lowered to `WARNING` in `alembic.ini`, removing the
  migration `INFO` messages.
- The internal scripts run in silent mode, eliminating the npm echo. The result
  is lean output, essentially the Vite URL and real errors.

### Typography and logo

- The site base font increased from 16px (browser default) to **18px** on
  `html`. Since the layout uses `rem` units, this scales text and spacing
  proportionally, without breaking the layout.
- The navbar logo grew: the full version (desktop) from 36px to 48px tall; the
  symbol (mobile) from 36px to 44px; the bar went from 56px to 64px tall to
  accommodate the larger logo.

### Theme: respect the system and persist correctly

- The theme now uses `localStorage` as the local source of truth, with
  `prefers-color-scheme` as the default on the first visit. So the site opens
  in dark mode when the operating system is in dark mode.
- The bug where the theme reverted to light mode on every page refresh was
  fixed. The root cause was twofold: the frontend relied solely on a network
  read, and the backend never returned the saved preferences. Now the choice
  survives the reload instantly, without depending on the network.
- A small script in `index.html` applies the theme before React mounts,
  avoiding the light-screen "flash" on reload.
- Backend contract fix: `GET /api/session-state` now returns the
  `preferences` block (theme + language). Before, `PUT /api/preferences`
  saved it, but `GET` never returned the value, so the preference was not
  restored. With this, the preference also syncs across machines.

### Language selector with real flags (SVG)

- The language selector showed "BR"/"US" instead of flags. The cause is a
  Windows limitation that does not include the flag emoji font, so the
  `🇧🇷`/`🇺🇸` emojis fall back to the letters.
- The solution was to replace the emojis with **vector SVG** flags
  (`FlagBR`/`FlagUS` components), which render consistently on any operating
  system, without adding dependencies and without using "fake" flag images.

### Removal of the "team palette" selector

- The old preferences panel had a blue/red/purple team palette selector. It was
  no longer part of the navbar; the orphan translation keys (`palette.*`) were
  removed from the `preferences.json` files (pt-BR and en). The site keeps its
  own color palette, working in light and dark mode.

## Automated evidence

- Frontend: `tsc --noEmit` (type-check) with no errors after the changes.
- Backend: the full suite ran with **177 tests passing** (1 real-lab test
  deselected by default).
- Live manual check: `GET /api/session-state` now returns
  `"preferences": { "theme": ..., "language": ... }` after a `PUT`; the backend
  responded `{"status":"ok"}` on `/health` and the frontend responded `200`.
- The development database was reset to defaults (light / pt-BR) after the
  manual tests.

## How to run (new flow)

```powershell
# from the repository root — starts backend + frontend + migration
npm run dev

# on a new machine, install everything first (a single node_modules at the root)
npm run setup
```

Frontend at `http://localhost:15173`, backend at `http://localhost:8010`.
